# Day 6 · Session 计划进度

`/plan <目标>` 先用结构化生成建立计划。进入执行后，`AgentSession.configurePlanRun` 同时准备两类模型输入。

- 系统消息给出最新计划、可引用的成功调用，以及何时提交进度的指令。
- 工具定义给出 `update_plan` 的名称、描述和参数 Schema，随 `request.tools` 发送。

模型通过响应中的 `toolCalls` 提交更新，下面是一个虚构的调用示例。真实运行的 ID 来自当前请求的证据引用。

```json
{
  "name": "update_plan",
  "arguments": {
    "operation": "set_status",
    "stepId": 0,
    "status": "completed",
    "evidence": [{ "runId": "example-run", "toolCallId": "1:1" }]
  }
}
```

`AgentRunner` 将调用交给本轮工具执行器。工具校验步骤与证据后调用 `TaskPlanner.updateStepStatus`，并把返回值写回 `draft.plan`。更新结果作为普通 tool 消息回传。下一次模型请求重新构造系统消息，展示更新后的步骤状态。会话正常返回后，历史和草稿一起提交。

纯计算等无需仓库事实的步骤使用 `set_status`，将状态设置为 `model_reported`，在 `summary` 中给出实际结果。如果模型用 `completed` 提交摘要且没有提供证据，程序也按 `model_reported` 保存该步骤。终端单独标出模型报告的步骤数。

程序校验调用来源及成功状态。证据是否足以支持步骤结论由模型判断，仓库分析仍需独立核对。模型直接回答时，终端按已提交的步骤状态显示进度。

## 模块职责与学习过程

| 模块                                                                 | 负责的状态或行为                                                                                     |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| [Core TaskPlanner](../../packages/core/src/planning/task-planner.ts) | 创建计划、校验步骤 ID、通过新快照更新状态或替换步骤。                                                |
| [CLI 结构化规划](../../apps/cli/src/commands/plan-demo.ts)           | 模型先返回目标和字符串数组。本地校验成功后才为步骤分配 ID 和初始状态。                               |
| [AgentSession](../../apps/cli/src/session/agent-session.ts)          | 持有已提交计划。每轮复制草稿、收集仓库工具证据，正常返回时提交计划与对话。取消或异常时丢弃本轮草稿。 |
| [AgentRunner](../../packages/core/src/agent/runner.ts)               | 为当前运行发布工具，在每次请求前重建动态上下文并检查预算，将模型产生的工具调用交给执行器。           |
| [update_plan](../../apps/cli/src/session/update-plan-tool.ts)        | 校验模型提交的状态、步骤 ID 和证据引用。替换时保留未改写步骤的 ID，给新增或改写的步骤分配新 ID。     |

本次讨论先确定会话边界，再沿真实请求看进度从哪里来。一次用户输入可触发多个模型请求与工具调用；用户下一条输入可以继续同一个计划。计划草稿归会话管理，终端负责展示已提交的状态。

1. **从计划生成开始。** `/plan` 的模型 JSON 只包含目标和步骤描述。步骤 ID 由程序分配。后续 `nextStepId` 用于显式替换时分配未使用的 ID，防止新步骤被旧工具历史引用。
2. **跟踪一次进度更新。** 系统提示给出计划与证据，工具 Schema 约定提交格式。模型用响应的 `toolCalls` 请求更新；执行器验证并修改草稿。一个步骤可以引用多个调用；同一次成功读取也能支持多个步骤。程序核对引用有效，结论是否得到支持还需对照工具正文。
3. **用异常场景区分证据与自述。** 学习者实测纯计算，得到 7 和 8，但旧版本因缺少仓库工具证据停在 0/4。增加 `model_reported` 后，纯计算可用摘要提交进度，终端明确标记模型报告。仓库工具调用仍须通过引用校验才能取得 `completed` 状态。
4. **用两轮真实会话复核。** 分别检查目录顺序、返回数量与截断、搜索位置、Git 状态，以及证据能否在下一轮继续使用。单项结果和组合回答分别验收，保留错误参数、遗漏行号和计划未完成的实际记录。

复习时先沿 `/plan` 跟踪到 `toolCalls`，再观察 `draft.plan` 的赋值和本轮结束后的提交。如果模型直接回答、返回了无效证据或耗尽请求预算，可对照终端进度和测试判断是哪个环节停止推进。

## 验证记录

- 离线环境为 Node.js v26.12.1、pnpm 10.34.7。`pnpm test` 构建并通过 35 个测试文件的 366 项测试。`pnpm typecheck` 与 `pnpm lint` 通过。全仓 `pnpm format:check` 报告既有的 `.vscode/settings.json` 格式问题。
- 真实模型为 Ollama 0.40.16、`qwen3:8b`，使用 `--context-length 16384 --think false --no-stream`。实测任务是分析本仓库 `apps/cli/src/main.ts` 的 `session` 子命令。
- 最初两轮约 35.5 秒和 52.5 秒，模型给出文本回答，计划均为 0/1。合并会话规则和动态计划为一条系统消息后，首轮约 38.5 秒。观察到 `read_file → update_plan(set_status) → 文本回复`，工具更新成功，进度 1/4。下一轮明确提示按证据更新进度，约 24.9 秒，观察到第二次成功的 `update_plan(set_status)`，进度 2/4。
- 真实复测覆盖计划启动、工具结果回传和跨轮提交，剩余两步仍待执行。完整仓库覆盖、截断说明和真实流式验证待验收。

纯计算回归使用同一模型与参数，输入 `/plan 计算1+2+3+c，假设 c = 1 或 2 时结果分别是多少？`。模型给出 7 和 8，约 30.3 秒后显示 `计划进度：4/4（模型报告 4 步）`。离线用例覆盖带结果摘要的完成报告、缺少摘要以及报告混入证据的拒绝路径。本次全量测试通过 367 项。

## 默认流式验收

- Fake Provider 分别以流式和非流式执行「读文件 → 引用真实调用完成步骤 → 下一次请求读到进度」。另验证替换后的计划超预算时，Runner 在下一次生成前返回 `BUDGET_EXCEEDED`，会话保留此前计划和历史。全量 369 项测试通过，构建、类型检查和 lint 通过。全仓格式检查仍报 `.vscode/settings.json`。
- 第一轮真实流式测试使用 Ollama 0.40.16、`qwen3:8b`、`--context-length 16384 --think false`。目录工具返回 50 项且 `truncated: true`，流式回答正确列出前 10 项并说明截断，但无依据地写了「实际共有 52 个路径」。模型成功读取根 `package.json`，一次计划更新因参数无效被拒，后续有多步以模型报告记入草稿。验收脚本等待 180 秒后结束，第一轮没有观察到提交，第二轮未运行。
- 缩小范围后复测同一模型和参数。首轮 53.5 秒，`list_directory` 返回 50 条且被截断。模型将 `evidence` 发成对象，Schema 拒绝；模型改成数组后，`update_plan` 成功保存工具证据。最终列出的前 10 项和截断标记正确，但把显示的 10 项误称为工具返回总数。初始规划仍生成了 4 步，首轮提交为 1/4。
- 第二轮 27.7 秒，沿用 1/4 的已提交计划。搜索定位到 `packages/core/src/agent/runner.ts`，搜索结果未截断，回答漏掉行号。模型给 `git_status` 传了不支持的 `path`，Schema 拒绝，回答未确认 Git 状态，也漏了第一轮截断的影响。会话正常退出；流式调用、Schema 拒绝与重试、证据更新和跨轮保留通过，真实回答完整性验收仍待通过。

## 工具说明修正后的流式复测

`list_directory` 增加 `returnedCount`，取实际返回数组的长度。它与回答展示的条数及目录总数分别计算。会话提示同时明确搜索位置使用 `path:line`、`git_status` 使用空对象、单个证据引用也必须放进数组。

- 同一模型与流式参数，目录轮 54.5 秒。模型按原顺序列对前 10 项，正确说明返回 50 项且已截断。首次 `update_plan` 成功保存工具证据，进度 1/5。
- 继续轮 44.4 秒。模型成功调用 `git_status({})`，正确报告工作区有未提交改动；再次说明了目录截断。搜索工具返回 `packages/core/src/agent/runner.ts:100`，合并回答仍漏了行号。初始计划把统计、提交和引用拆成了额外步骤，最终进度 1/5。
- 单独请求模型按 `path:line` 输出搜索结果，5.3 秒后实际回答包含正确的 `packages/core/src/agent/runner.ts:100`。行号单项通过，组合问题的回答完整性仍未通过。

## 主流程复核与后续事项（2026-11-18）

Issue #6 的 TaskPlan 最小主流程已接通。覆盖初始计划校验、稳定步骤 ID、最新计划注入与预算、显式推进／重开／替换、成功工具引用校验、提前结束提示、跨轮提交与失败回滚，以及重置。真实模型已验证流式与非流式的更新链路。组合仓库分析仍有行号遗漏及计划未全部完成，阶段 A 的真实回答完整性验收保持开放。

- **计划粒度与组合回答。** 避免把「调用 update_plan」「填写证据 ID」拆成用户任务步骤。用固定的目录、截断、搜索位置和 Git 状态清单复核组合回答。属于模型规划与指令遵循的后续评测。
- **证据与上下文裁剪。** 当前计划保存引用，工具正文位于历史消息；裁掉旧用户轮次时，引用仍可能保留。和 [#29](https://github.com/BernardZhang/ts-code-agent/issues/29) 一起评估将引用与工具结果直接关联，以及裁剪后隐藏或标记不可见证据。
- **模型报告的计数。** 当前终端单独标出模型报告的步数，但它仍计入总进度，且仓库步骤能被模型标为自述完成。若后续把计划进度用于任务成功判定，须先明确哪些步骤要求工具证据，并以独立验收核对证据能否支持结论。
- **补充定向回归。** 增加计划已更新之后的 Ctrl+C 回滚及步数上限提交测试。当前已有会话取消、计划异常回滚和步数上限历史提交测试。
